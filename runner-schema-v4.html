RUNNER · SCHEMA v4 · DEVELOPER GUIDE

    
What changed & why

  


  

    
BACKEND NOTE

    

      
Live app today: travels2, trips, trip_passengers, vans, locations, crew_members.

      
Near-term schema direction: organisations, projects, shoot_days, day_crew, later sheet_documents.

      
Phase labels in this doc are only rough sequencing for a two-person team. They are not meant as strict rollout boundaries.

    

  


  

    
BACKEND CHECKLIST

    

      
1. Treat travels2 as the live source of truth for runs.

      
2. Add project_id to travels2 for direct project scoping.

      
3. Add shoot_day_id to travels2 for day linkage.

      
4. Keep trips scoped by travel_id only; do not add duplicate project_id or shoot_day_id there unless a real query/perf problem appears.

      
5. Keep location_id + travel_type semantics as the live contract until the app actually writes separate endpoint columns.

    

  


  
  

    
CHANGELOG — v3 → v4

    

      
REMOVEDtransport_notifications — Deleted entirely. The notification layer (SMS/push per pickup) needs a comms infrastructure that doesn't exist yet. Will return in a future phase once transport is stable and in use.

      
REMOVEDdriver_checkins — Deleted entirely. Real-time driver GPS is Phase 3. Requires mobile, Supabase Realtime, and opt-in location flow. Don't model what you're not building yet.

      
KEPTshoot_days — Keeping the existing table name for now to avoid unnecessary migrations. UI copy can still say "Day 2", but DB/code stay on shoot_days and shoot_day_id.

      
RENAMEDcall_sheets → sheet_documents — Keep the better name in the doc, but treat it as later work rather than current backend contract.

      
RENAMEDcall_sheet_crew → day_crew — Keep crew attached to the shoot day, not to a document. This is still the intended direction.

      
MOVED TO FUTUREsheet_documents, departments — Keep these visible for orientation, but they are not part of the live app contract.

      
NEWorganisations — Top of every hierarchy. Phase 1: any authenticated user sees all orgs and all data (open by design). Phase 2: add org_members and tighten RLS — single policy swap, no migration.

      
NEWprojects — A named production under an org. "Britain's Got Talent" is a project. Has a client field (the broadcaster/brand) separate from the org (the production company).

      
NEWday_crew — Keep this in the document as the intended day-level crew table, but do not confuse it with the current transport runtime tables.

      
NEWshoot_days.project_id — The existing shoot_days table now links directly to projects so transport planning hangs off the production day, not off any document.

      
NEWproject-scoped vans — Product direction stays the same: treat vans as rentals by default and use past projects only as suggestions. The live DB table is still leaner than that direction today.

    

  


  
  

    
PRODUCTION STRUCTURE — PLANNED DIRECTION

    


      

        
organisations

        
Top-level tenant. Phase 1 = open read/write for any authenticated user. Phase 2 = invite-only via org_members.

        
CREATE TABLE organisations (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  slug        text UNIQUE NOT NULL,  -- url-safe: "bbc-studios", "meisel-film"
  created_at  timestamptz DEFAULT now()
);

ALTER TABLE organisations ENABLE ROW LEVEL SECURITY;

-- Phase 1: open — any authed user can CRUD
CREATE POLICY "authed_all" ON organisations
  FOR ALL USING (auth.role() = 'authenticated')
  WITH CHECK (auth.role() = 'authenticated');

        
Phase 2 migration: add org_members(org_id, profile_id, status) and replace the policy with auth.uid() IN (SELECT profile_id FROM org_members WHERE org_id = organisations.id AND status = 'active'). No data migration needed.

      


      

        
projects

        
A named production under an org. "Britain's Got Talent" is a project. The org is the production company; the client is the broadcaster or brand they're working for.

        
CREATE TABLE projects (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id      uuid NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
  name        text NOT NULL,           -- "Britain's Got Talent"
  client      text,                    -- NULL — "BBC"
  status      text DEFAULT 'active',   -- active | wrapped | archived
  created_at  timestamptz DEFAULT now()
);

CREATE INDEX ON projects (org_id);

ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
CREATE POLICY "authed_all" ON projects
  FOR ALL USING (auth.role() = 'authenticated')
  WITH CHECK (auth.role() = 'authenticated');

      


      

        
shoot_days

        
One calendar day of a production. This is still the intended place to anchor day-level planning, even though the current app transport runtime is not wired to it yet.

        
CREATE TABLE shoot_days (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id       uuid NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
  project_id   uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  shoot_date   date NOT NULL,
  day_number   int,               -- NULL ok for single-day jobs; "Day 2" = 2
  title        text,              -- NULL — optional: "Berlin Exteriors"
  status       text DEFAULT 'draft',  -- draft | locked | wrapped
  created_at   timestamptz DEFAULT now()
);

CREATE INDEX ON shoot_days (project_id);
CREATE INDEX ON shoot_days (org_id);

ALTER TABLE shoot_days ENABLE ROW LEVEL SECURITY;
CREATE POLICY "authed_all" ON shoot_days
  FOR ALL USING (auth.role() = 'authenticated')
  WITH CHECK (auth.role() = 'authenticated');

        
Migration note: Keep the existing shoot_days table name. Add project_id (NOT NULL after backfill). The live app transport tables are still separate and need an explicit link later.

      


      

        
day_crew

        
Crew work 12h shifts on a shoot day, not on a document. Keep this as the intended planning table for call times and transport grouping.

        
CREATE TABLE day_crew (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id          uuid NOT NULL REFERENCES organisations(id) ON DELETE CASCADE,
  shoot_day_id    uuid NOT NULL REFERENCES shoot_days(id) ON DELETE CASCADE,
  crew_member_id  uuid NOT NULL REFERENCES crew_members(id) ON DELETE CASCADE,
  call_time       timetz NOT NULL,
  role_title      text,
  transport_note  text,
  location_id     uuid REFERENCES locations(id) ON DELETE SET NULL,
  created_at      timestamptz DEFAULT now()
);

CREATE INDEX ON day_crew (shoot_day_id);
CREATE INDEX ON day_crew (crew_member_id);

ALTER TABLE day_crew ENABLE ROW LEVEL SECURITY;
CREATE POLICY "authed_all" ON day_crew
  FOR ALL USING (auth.role() = 'authenticated')
  WITH CHECK (auth.role() = 'authenticated');

        
Keep this day-level even if sheet_documents arrive later. One crew member should still have one call time per shoot day.

      


    

  


  
  

    
LIVE TRANSPORT CONTRACT — CURRENT APP

    

      
travels2 — Live table used by the app today. Current payload is van_id, travel_type, location_id, scheduled_time, sort_order, notes. Near-term additions should be project_id and shoot_day_id. No persisted start_location, start_time, destination_id, or driver_crew_id yet.

      
travel_type + location_id — pickup means the chosen location is the final destination. dropoff means the chosen location is the start point.

      
scheduled_time — Semantics depend on type: pickup = "arrive by", dropoff = "depart at". The UI enforces arrival time for pickups only.

      
vans, locations, crew_members — The live app currently uses lean standalone tables. Project/org/day scoping is still product direction, not the active DB contract.

    

  


  

    
LOCATION + TYPE SEMANTICS

    

      
travels2 row
  travel_type   = 'pickup'
  location_id   = Heathrow T5
  scheduled_time = 08:30
  meaning       = arrive at Heathrow T5 by 08:30

travels2 row
  travel_type   = 'dropoff'
  location_id   = Broadcast Centre
  scheduled_time = 18:15
  meaning       = depart from Broadcast Centre at 18:15

      
This is why the live app can derive destinationAddress for pickups and startLocation for dropoffs without storing separate DB columns.

Later normalization if needed
  project_id       -- direct project scoping on the run
  shoot_day_id     -- explicit day linkage
  driver_crew_id   -- explicit assigned driver

Trips stay simple
  travel_id only
  no duplicate project_id / shoot_day_id for now

Rule:
  do not document these later columns as live until the app reads/writes them.

NAMING CONVENTIONS

    

      
DB / Code:  shoot_days  travels2  trips  day_crew  sheet_documents

      
UI labels:  "Day"  "Run"  "Stop"  "Crew"  "Call Sheet"

      
"Run" is what a 1st AD calls a travel on set. Never use it in code or column names — code always uses travel. The split is intentional and documented.

      
Phase 1 auth rule (applies to ALL tables): Any authenticated Supabase user has full CRUD on everything. This is intentional — ship fast, gate later. The RLS structure is already positioned for Phase 2 tightening with a single policy swap per table. No data migration needed when that time comes.
